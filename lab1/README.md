# Лабораторна 1. Моделювання банківського рахунку з багатопотоковим доступом

Програма моделює рахунок, до якого одночасно звертаються кілька клієнтів (потоків):
поповнення, зняття, перевірка достатності коштів, журнал транзакцій. Порівнюються
дві реалізації - **без синхронізації** (гонка даних) та **з `threading.Lock`**.

> Виконав: _ПІБ, група_ (заповнити)

## Запуск

Потрібен лише Python 3.10+ (сторонні бібліотеки не потрібні).

```powershell
python bank_simulation.py            # повний набір експериментів
python bank_simulation.py --quick    # скорочений варіант (швидше)
python bank_simulation.py --out results   # зберегти CSV в інший каталог (він має існувати)
```

Результати виводяться таблицями в консоль і зберігаються у `results_scaling.csv`
та `results_timing.csv`.

## Як це працює

| Компонент | Призначення |
|---|---|
| `BankAccount` | база: початковий баланс, журнал `Transaction` |
| `UnsafeBankAccount` | без захисту: **втрачені оновлення** при поповненні (read -> write) та **TOCTOU** при знятті (перевірка встигає застаріти) |
| `SafeBankAccount` | перевірка, зміна балансу й запис у журнал виконуються атомарно під одним `threading.Lock` |
| `client_worker` | потік-клієнт, виконує випадкові поповнення/зняття; усі потоки стартують одночасно (`Barrier`) |
| `run_simulation` | один запуск; порівнює фактичний баланс з очікуваним |

**Очікуваний баланс** = початковий + сума поповнень - сума зняттів, які клієнти отримали як успішні.
Різниця з фактичним балансом - це кількість "загублених" або "створених нізвідки" грошей.
Додатково перевіряється журнал: чи кожна операція змінила баланс рівно на свою суму та чи не було від'ємних балансів.

Для відтворюваності набір операцій генерується з seed і однаковий для обох версій.

### Важливо про GIL

У CPython потоки перемикаються рідко, тому гонка без затримок проявляється нерегулярно
(у вимірюваннях - 0 помилок із 5 запусків). Щоб відтворити реальну ситуацію (звернення до БД/мережі
між читанням і записом), між читанням і записом додано `time.sleep(0)` ("вікно гонки").
Помилка в алгоритмі при цьому та сама; затримка лише робить її помітною.

## Результати (коротко)

- **Коректність.** Без синхронізації похибка балансу з'являлась у всіх запусках від 2 потоків;
  з `Lock` - завжди 0, баланс не ставав від'ємним, журнал узгоджений. З 1 потоком обидві версії коректні.
- **Кількість потоків і операцій.** Похибка швидко зростає з кількістю потоків та операцій на потік
  (більше конкурентних звернень - більше втрачених оновлень).
- **Вартість блокування.** `Lock` повільніший за версію без синхронізації приблизно в 1.2-1.4 раза
  (у деяких вимірюваннях з латентністю - більше через конкуренцію за замок). Це ціна коректності.
  Час вимірюється в мілісекундах і шумить, тому дивіться на тренд, а не на окремі цифри.
